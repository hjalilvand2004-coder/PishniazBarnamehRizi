# برگهٔ هماهنگی ورود یکپارچه (SSO) — سامانهٔ دانشجو۳۶۰

**مرجع:** «راهنمای اتصال سامانه‌ها به ورود یکپارچهٔ دانشجویار۳۶۰» — نسخهٔ ۱٫۰ (مطابق پرتال x.3.2)
**نسخهٔ سامانه:** 2.5.0 — **وضعیت انطباق:** ✅ منطبق کامل (۱۸/۱۸ چک سبز با راستی‌آزمایی زنده)

---

## ۱) مقادیر ثبت کلاینت — برای ارسال به مدیر پرتال

طبق بخش ۴ و ۱۱ راهنما، ثبت کلاینت فقط توسط مدیر پرتال در `data/clients.json` انجام می‌شود.
مدیر پرتال باید مقادیر زیر را **دقیقاً به همین شکل** ثبت کند (همین جدول در داشبورد → تنظیمات سامانه نمایش و کپی می‌شود):

| فیلد | مقدار |
|---|---|
| client_id | `daneshjo360` |
| نوع کلاینت | `confidential: false` (عمومی — PKCE/S256، بدون secret) |
| redirect_uri | `http://<PUBLIC_ORIGIN>/auth/sso/callback` (فعلاً تست: `http://127.0.0.1:8000/auth/sso/callback`) |
| post_logout_redirect_uri | `http://<PUBLIC_ORIGIN>/login?logout=1` |
| backchannel logout URL | `http://<PUBLIC_ORIGIN>/auth/sso/backchannel` |
| scope درخواستی | `openid profile email` |
| نقش‌های لازم در کاتالوگ (app_key) | `daneshjo360.access`، `daneshjo360.sysadmin`، `daneshjo360.edu_manager`، `daneshjo360.dept_manager` |

نکات ثبت:
- `redirect_uri` باید **کاراکتر به کاراکتر** با ثبت پرتال یکی باشد؛ در نشست لوکال `127.0.0.1:8000` و در استقرار رسمی، نشانی عمومی سامانه (PUBLIC_ORIGIN). مقدار مؤثر هر زمان از پنل «تنظیمات سامانه» یا `GET /api/settings` خوانده می‌شود و قابل ویرایش است.
- نقش‌ها فقط از `resource_access.<client_id>.roles` خوانده می‌شوند؛ پیشوند نقش‌ها برابر client_id است (متغیر محیطی `DANESHJO360_SSO_APP_KEY` فقط برای جداسازی اختیاری).
- ورود نمایشی (demo) تا زمان ثبت کلاینت برای ارزیابی سامانه فعال است و پس از استقرار رسمی با `DANESHJO360_DEMO_LOGIN=0` خاموش می‌شود.

## ۲) نکات استقرار (بخش ۳ راهنما)

- استقرار رسمی روی **HTTPS** الزامی است؛ استفادهٔ فعلی از HTTP فقط در شبکهٔ داخلی/تست قابل‌قبول است.
- session cookies با `HttpOnly` + `SameSite` و secure خودکار روی https صادر می‌شوند؛ توکن‌ها فقط سمت سرور در پایگاه دادهٔ نشست نگه داشته می‌شوند (نه localStorage).
- هیچ اعتبارسنجی JWT در مرورگر انجام نمی‌شود؛ همهٔ اعتبارسنجی‌ها سمت سرور است.

## ۳) چک‌لیست راه‌اندازی (بخش ۱۳ راهنما) — وضعیت پیاده‌سازی

| # | الزام راهنما | وضعیت در سامانه |
|---|---|---|
| ۱ | انتخاب client_id، نوع کلاینت و نهایی‌کردن با مدیر پرتال | ✅ `daneshjo360` (public) — **ثبت در پرتال در انتظار مدیر پرتال** |
| ۲ | ثبت کلاینت در data/clients.json توسط مدیر پرتال | ⏳ با برگهٔ بالا |
| ۳ | مسیر callback با اعتبارسنجی state | ✅ `GET /auth/sso/callback` — state جلسه‌ای تک‌مصرف، انقضا ۹۰۰ ثانیه، کنترل iss |
| ۴ | PKCE S256 + ریدایرکت به Authorize با scope کامل | ✅ verifier ۶۴ نویسه، `code_challenge_method=S256`، scope=`openid profile email` |
| ۵ | تبادل کد در token endpoint، دریافت سه توکن | ✅ grant_type=authorization_code + code + redirect_uri + client_id + code_verifier |
| ۶ | اعتبارسنجی کامل id_token (RS256, kid, iss, aud, exp, nonce) با JWKS | ✅ PyJWKClient با کش کلید و چرخش kid؛ nonce اجباری |
| ۷ | جلسهٔ محلی امن (HttpOnly + SameSite) و اتصال به sub | ✅ کوکی امن + `sub` UUID پایدار مبنای رکورد کاربر |
| ۸ | نوسازی با refresh_token تک‌مصرف و جایگزینی | ✅ چرخش فوری؛ reuse توکن کهنه → ابطال کامل نشست (پادزهر سرقت) |
| ۹ | نقش‌ها فقط از resource_access.<client_id>.roles | ✅ فیلتر دقیق روی نقش‌های همین کلاینت |
| ۱۰ | خروج: ابطال جلسهٔ محلی + نقطهٔ پایانی logout | ✅ RP-initiated با post_logout_redirect_uri + id_token_hint + پذیرش Backchannel Logout |
| ۱۱ | تست سناریوهای خطا (جدول ۵) و نرخ‌گذاری | ✅ پیام‌های فارسی اختصاصی؛ نرخ‌ها: ورود ۱۰/۳۰۰s، توکن ۶۰/۶۰s برای هر IP |
| ۱۲ | ثبت سامانه با client_id در پنل مدیریت پرتال | ⏳ پس از ثبت توسط مدیر پرتال |
| ۱۳ | قلب‌های سه‌گانهٔ نمایشی و تست نهایی ورود | ⏳ پس از ثبت کلاینت |

**راستی‌آزمایی زنده:** داشبورد → تنظیمات سامانه → «راستی‌آزمایی انطباق با راهنما» (یا `GET /api/settings/sso/compliance`) — سند Discovery سرور واقعی و پیاده‌سازی این سامانه را در ۱۸ چک بررسی می‌کند؛ در نسخهٔ 2.5.0 همهٔ چک‌ها سبز است.

## ۴) رفتار سامانه در سناریوهای خطا (جدول ۵ راهنما)

| خطای سرور | پیام فارسی نمایش‌داده‌شده |
|---|---|
| invalid_client (کلاینت ناشناخته یا دامنهٔ نامطابق) | «کلاینت SSO شناخته نشد؛ client_id یا نوع کلاینت با مقدار ثبت‌شدهٔ پرتال یکی نیست. مقادیر برگهٔ هماهنگی را با مدیر پرتال نهایی کنید.» |
| invalid_grant (verifier/کد مصرف‌شده یا نامعتبر) | «کد مجوز یا code_verifier نامعتبر است یا قبلاً مصرف شده؛ لطفاً از نو وارد شوید.» |
| PKCE الزامی است (challenge غایب/غیر S256) | درخواست اصلاً با S256 ساخته می‌شود؛ در خطای invalid_request توضیح دقیق سرور نمایش داده می‌شود |
| redirect_uri ناهمسان | ورود اصلاً آغاز نمی‌شود تا نشانی ثبت‌شدهٔ پرتال با تنظیمات سامانه یکی شود؛ بررسی یکسان‌بودن با «تست مرکز احراز هویت» |
| access token منقضی | نوسازی خودکار با refresh_token (تک‌مصرف) |
| ۴۲۹ در ورود (۱۰ در ۵ دقیقه برای هر IP) | «تعداد تلاش‌ها بیش از حد مجاز است؛ لطفاً کمی بعد دوباره تلاش کنید.» |

## ۵) نرخ‌گذاری‌ها (بخش ۱۰ راهنما)

- ورود: ۱۰ درخواست در ۵ دقیقه برای هر IP (`DANESHJO360_LOGIN_RATE`)
- توکن/نوسازی: ۶۰ درخواست در دقیقه برای هر IP (`DANESHJO360_REFRESH_RATE`)
- پیاده‌سازی سمت سامانه با پنجرهٔ لغزان در حافظه؛ مطابق قواعد سرور SSO

## ۶) ملاحظات امنیتی اعمال‌شده (بخش ۱۰ راهنما)

- کلاینت public است؛ هیچ secret در مرورگر یا کد قرار نمی‌گیرد و PKCE اجباری است.
- state و nonce جلسه‌ای، تک‌مصرف و با انقضا هستند و در callback با مقدار ذخیره‌شده تطبیق داده می‌شوند.
- refresh_token هرگز در مرورگر ذخیره نمی‌شود؛ فقط در پایگاه دادهٔ نشست سمت سرور.
- لاگ‌ها و پیام‌های خطا هیچ توکن یا claim حساسی را در بر ندارند.

## ۷) گام‌های باقی‌مانده (سمت پرتال)

1. ثبت کلاینت مطابق جدول ۱ در `data/clients.json` / پنل مدیریت پرتال.
2. فعال‌سازی گار (gate) سامانه در صفحهٔ تست پرتال.
3. ورود واقعی با حساب آزمایشی دارای نقش‌های `daneshjo360.*` و تایید نهایی (قلب‌های سه‌گانهٔ نمایشی).
4. اعلام `PUBLIC_ORIGIN` نهایی استقرار در صورت تغییر نشانی، تا redirect/backchannel با همان مقدار بازثبت شود.
