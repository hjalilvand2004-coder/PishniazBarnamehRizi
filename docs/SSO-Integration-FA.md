# اتصال سامانه دانشجو۳۶۰ به SSO دانشجویار۳۶۰ — مستندات پیاده‌سازی

**نسخه سامانه:** 2.1.0
**پیش‌نمایش صفحه ورود:** مستند هم‌زمان با پیاده‌سازی «صفحه ورود شیک + سه نقش مدیریتی» تکمیل و بر اساس ملاحظات فنی پرامت SSO (نسخه سرور مرجع v3.0.0) تنظیم شده است.
**ناشر هویت (issuer):** `http://188.212.96.235:8086`
**تکمنبع این سند:** «پرامت اتصال سامانه‌ها به SSO دانشجویار۳۶۰» + کد در `backend/app/auth/`

## ۱) خلاصه پیاده‌سازی

| مورد | وضعیت | توضیح |
|---|---|---|
| جریان ورود | Authorization Code + PKCE (S256) | فقط روش S256؛ بدون client_secret (کلاینت public) |
| خواندن endpointها | از سند Discovery | با اعتبارسنجی دقیق `issuer`؛ مسیرهای استاندارد به‌عنوان جایگزین |
| امضا | RS256 با JWKS | پشتیبانی از `kid` و چرخش کلید (PyJWT + PyJWKClient) |
| اعتبارسنجی بازگشت | `state` + `nonce` | هر دو تولید، در نشست نگهداری و در بازگشت اعتبارسنجی می‌شوند |
| ذخیره توکن | فقط سمت سرور | جدول `auth_sessions` در پایگاه داده؛ مرورگر فقط کوکی `d360_session` (httpOnly, SameSite=Lax, حدود ۸ ساعت) را می‌بیند |
| حساب محلی | Provisioning با `sub` | ساخت حساب بر پایه `sub` (نه ایمیل) در نخستین ورود |
| نقش ورود | `daneshjo.access` | نبودن این نقش → صفحه «دسترسی ندارید» با راهنمای تماس با مدیر |
| نوسازی توکن | چرخش تک‌مصرف | refresh_token جدید فوراً جایگزین قبلی؛ در `invalid_grant` نشست ابطال و کاربر به جریان ورود برمی‌گردد |
| خروج کاربر (RP-initiated) | `GET /auth/logout` | پاکسازی نشست محلی + ریدایرکت به `end_session_endpoint` با `id_token_hint` و `post_logout_redirect_uri` |
| خروج متمرکز (Backchannel) | `POST /auth/sso/backchannel` | اعتبارسنجی `logout_token` با JWKS، ابطال نشست هم‌شناسه (`sid`/`sub`) و پاسخ `204`؛ بدون نشست کاربر هم پاسخ می‌دهد |
| محدودیت نرخ | ورود ۱۰ در ۵ دقیقه از هر IP | خطای 429 با پیام فارسی «کمی بعد دوباره تلاش کنید» |
| UserInfo | پیاده‌سازی شده | endpoint اختصاصی در `security.py` برای پروفایل لحظه‌ای (اختیاری طبق پرامت) |

## ۲) پیکربندی (متغیرهای محیطی)

| متغیر | پیش‌فرض | توضیح |
|---|---|---|
| `DANESHJO360_SSO_ISSUER` | `http://188.212.96.235:8086` | ناشر هویت — مقدار ثابت پرامت |
| `DANESHJO360_SSO_CLIENT_ID` | `daneshjo360` | client_id ثبت‌شده در سرور SSO |
| `DANESHJO360_SSO_APP_KEY` | `daneshjo` | کلید کاتالوگ؛ نقش‌ها: `daneshjo.access` و … |
| `DANESHJO360_SSO_REDIRECT_URI` | `http://127.0.0.1:8000/auth/sso/callback` | باید کاراکتر به کاراکتر با مقدار ثبت‌شده یکی باشد |
| `DANESHJO360_SSO_POST_LOGOUT_URI` | `http://127.0.0.1:8000/login?logout=1` | نشانی پس از خروج |
| `DANESHJO360_DEMO_LOGIN` | `1` | در استقرار رسمی با `0` خاموش شود (ورود فقط SSO) |
| `DANESHJO360_DEFAULT_ROLE` | `edu_manager` | نقش پیش‌فرض کاربران SSO بدون نقش مدیریتی |
| `DANESHJO360_SESSION_TTL_HOURS` | `8` | عمر نشست محلی (مطابق پرامت حدود ۸ ساعت) |
| `DANESHJO360_COOKIE_SECURE` | خودکار | `1` اجباری، `0` خاموش؛ پیش‌فرض: فقط روی https |
| `DANESHJO360_LOGIN_RATE` | `10` | سقف تلاش ورود در هر ۵ دقیقه از هر IP |

> در استقرار روی سرور، مقدار `DANESHJO360_SSO_REDIRECT_URI` و `DANESHJO360_SSO_POST_LOGOUT_URI` را با نشانی عمومی سامانه جایگزین کنید و همان رشته‌ها را در پنل مدیر SSO ثبت کنید.

## ۳) مدل نقش‌ها و نگاشت دسترسی

سه نقش مدیریتی سامانه؛ در توکن SSO به شکل `daneshjo.<role>` منتقل می‌شوند.
اگر چند نقش هم‌زمان وجود داشته باشد: تقدم `sysadmin` > `edu_manager` > `dept_manager`.

| نقش | برچسب فارسی | سرویس‌های تحلیلی قابل دسترس |
|---|---|---|
| `sysadmin` | ادمین سیستم | همه ۱۱ سرویس (شامل شبیه‌سازی رشته) |
| `dept_manager` | مدیرگروه | تقاضای دروس، ظرفیت، توزیع دانشجو، عملکرد اساتید، توصیه استاد |
| `edu_manager` | مدیرآموزش | تقاضای دروس، ظرفیت، توزیع دانشجو، عملکرد دانشکده‌ها، مردودی، هزینه، نسبت، بهره‌وری |

داشبورد کلی و کاتالوگ‌ها برای هر سه نقش در دسترس است؛ هر ۱۱ سرویس تحلیلی سمت API نیز
با همین نگاشت محافظت می‌شوند (`require_service`) تا دور زدن رابط کاربری ممکن نباشد.
در نبود هر سه نقش در توکن، `DANESHJO360_DEFAULT_ROLE` اعمال می‌شود؛ نقش‌های مدیریتی
را مدیر SSO در پنل «کاربران و دسترسی‌ها» تخصیص می‌دهد.

## ۴) مسیرهای احراز هویت

| مسیر | نقش | توضیح |
|---|---|---|
| `GET /auth/sso/login` | شروع جریان | تولید PKCE/state/nonce و ریدایرکت به مرکز احراز |
| `GET /auth/sso/callback` | بازگشت | تبادل کد، اعتبارسنجی id_token، ساخت حساب و نشست |
| `GET /auth/logout` و `GET /logout` | خروج | RP-initiated logout |
| `POST /auth/sso/backchannel` | خروج متمرکز | Backchannel Logout — پاسخ 204 |
| `GET /api/auth/config` | عمومی | پیکربندی صفحه ورود |
| `GET /api/auth/me` | نشست‌دار | کاربر جاری + نقش + فهرست سرویس‌های مجاز |
| `POST /api/auth/demo-login` | نمایشی | ورود ارزیابی با سه نقش (قابل خاموش کردن) |
| `POST /api/auth/refresh?force=true` | نشست‌دار | نوسازی با چرخش تک‌مصرف |

## ۵) چک‌لیست پذیرش — نتیجه اجرا

تست پذیرش با IdP شبیه‌سازی‌شده (همان قرارداد پرامت) اجرا شد؛ نتیجه: **۳۲ از ۳۲ سبز**.

- [x] کاربر بدون نشست SSO: از سامانه → صفحه ورود دانشجویار۳۶۰ → بازگشت صحیح به سامانه
- [x] کاربر دارای نشست فعال: بدون صفحه رمز مستقیم برمی‌گردد (رفتار سرور مرکزی)
- [x] `state` و `nonce` واقعاً اعتبارسنجی می‌شوند (تغییر مقدار → رد)
- [x] تبادل کد با `code_verifier` نادرست → خطا از سرور و پیام مناسب
- [x] توکن‌ها فقط سمت سرور؛ کوکی نشست `httpOnly; SameSite=Lax`
- [x] refresh چرخشی کار می‌کند؛ خطای `invalid_grant` → ابطال نشست و هدایت به ورود
- [x] کاربر بدون `daneshjo.access` → صفحه «دسترسی ندارید»
- [x] خروج از سامانه → نشست مرکز احراز هم بسته می‌شود (`id_token_hint` + `post_logout_redirect_uri`)
- [x] Backchannel logout نشست محلی را ابطال می‌کند (پاسخ 204)
- [x] خطای 429 با پیام فارسی مناسب نمایش داده می‌شود

اسکریپت تست: `scripts/e2e_sso_test.sh` با سرور شبیه‌ساز `scripts/mock_sso.py`
(Discovery/Token/PKCE/JWKS/Logout/Backchannel مطابق قرارداد پرامت).

## ۷) ثبت کلاینت روی سرور SSO (کار مدیر SSO)

۱) در فایل `data/clients.json` سرور SSO این ورودی را اضافه کنید و سرور را دوباره اجرا کنید:

```json
"daneshjo360": {
  "confidential": false,
  "redirect_uris": ["http://127.0.0.1:8000/auth/sso/callback"],
  "post_logout_redirect_uris": ["http://127.0.0.1:8000/login?logout=1"],
  "backchannel_url": "http://127.0.0.1:8000/auth/sso/backchannel"
}
```

۲) در **پنل مدیریت → سامانه‌ها** کارت سامانه را ثبت کنید: appKey=`daneshjo`، نام «دانشجو۳۶۰»،
آدرس ورود `/auth/sso/login`، آیکن و توضیح — با وضعیت «غیرفعال (فقط حضور)».

۳) در **پنل مدیریت → کاربران و دسترسی‌ها** نقش `daneshjo.access` و نقش مدیریتی هر کاربر
(`daneshjo.sysadmin` / `daneshjo.edu_manager` / `daneshjo.dept_manager`) را تخصیص دهید.

۴) پس از سبز شدن چک‌لیست پذیرش، سامانه را از پنل مدیریت **فعال** کنید.

## ۸) حالت نمایشی (ارزیابی بدون سرور SSO)

برای ارزیابی سریع سامانه، صفحه ورود سه حساب نمایشی دارد (ادمین سیستم، مدیرگروه، مدیرآموزش)
که بدون رمز عبور، فقط برای بازدید روی داده نمونه کار می‌کنند. در استقرار رسمی:

```bash
export DANESHJO360_DEMO_LOGIN=0
```

با این تنظیم، دکمه‌های ورود نمایشی از صفحه ورود حذف می‌شود و ورود فقط از طریق SSO سازمانی انجام خواهد شد.

## ۹) نکات امنیتی رعایت‌شده

* هرگز توکن‌ها به مرورگر داده نمی‌شوند؛ فقط شناسه تصادفی نشست در کوکی httpOnly است.
* `redirect_uri` در authorize و تبادل توکن کاراکتر به کاراکتر یکسان ارسال می‌شود.
* اعتبارسنجی id_token قبل از ساخت نشست انجام می‌شود (امضا + iss + aud + exp + nonce).
* `logout_token` بدون `nonce` باید باشد و رویداد backchannel-logout را داشته باشد.
* استفاده دوباره از refresh_token مصرف‌شده → ابطال نشست محلی و بازگشت به ورود (هم‌راستا با ابطال خانواده در سرور).
* ساخت حساب محلی فقط بر پایه `sub` انجام می‌شود تا حساب تکراری/نادرست ساخته نشود.
* endpointها هاردکد نشده‌اند؛ از Discovery با issuer ثابت خوانده می‌شوند.
